# CLAUDE.md — qualio-action

The GitHub Action (composite, `action.yml`) that customers' `.github/workflows/qualio.yml` calls to run Qualio's generated Playwright tests on their own runners and report to Qualio. Product rules live in the global `../CLAUDE.md`; the platform is `../qualio-webapp`.

## Contract with qualio-webapp

- **Workflow → action:** Qualio writes the workflow in `../qualio-webapp/packages/agents/src/coder/scaffold.ts` (`servedWorkflowFile()`, `QUALIO_ACTION_REF`). It passes `api-key`, `api-url`, `base-url` and the `config` block (with `tests.path`), grants `contents: write` (only for Qualio's `qualio/*` branches) and passes the test accounts' passwords as `test-passwords: ${{ secrets.QUALIO_TEST_PASSWORDS }}` (older workflows put per-role `E2E_<ROLE>_USERNAME/_PASSWORD` secrets in the job-level `env`; those still win). `tests-source` is ignored (a notice asks to remove it) and `working-directory` is the folder only when the config doesn't set `tests.path`.
- **Tests live in the repository** ([spec](../specs/tests-in-the-repository.md)): `prepare` (step *Prepare the tests*) asks `/v1/tests/prepare` for the folder (`testsDir`, `managed`: qualio.yml's `tests.path` wins over `working-directory`; `moving`: the project's tests are still in Qualio), sends `/v1/tests/snapshot` (`files: [{ path, sha256 }]`, then again with `content` for the hashes Qualio answers `missing`; never `node_modules`, Playwright's output or `.qualio`), and writes the answer's `files` (Qualio's open changes on the branch; `content: null` deletes) on top of the checkout. A binary file (a NUL byte near the start or not UTF-8: a committed `.xlsx`, a PDF) is sent as a text description instead (`scripts/binary.mjs`: `[qualio:binary]` with its kind, size and sha256, and a workbook's sheets and first rows; the marker is `@qualio/shared`'s `BINARY_FILE_MARKER` in qualio-webapp, keep them in step), with its bytes' hash (`bytesSha256`), and `applyFiles` never writes text over a binary file nor deletes one (a warning). Since v1.7.0 (phase 63, [spec](../specs/test-files-from-people.md)) the action sends `binary: true` on `/v1/tests/snapshot`, `/v1/tests/changes` and `/v1/pr/outbox`, and Qualio may send a binary file it adds (a test file a person attached) as `{ path, content: <base64>, encoding: 'base64' }`: `applyFiles` writes its bytes, `fileAt` returns bytes (conflicts judged by the bytes' hash, `changeHash`), `suggest` skips it, and `qualioPullRequest` uploads it with `POST git/blobs` (`encoding: base64`) and puts its sha in the tree. `notices` in an answer are printed as warnings. `test/prepare.test.mjs` (with `test/data/students.xlsx`) and `test/changes.test.mjs` (stub mode `changes-binary`) cover it. Without the folder: a `moving` project gets the whole folder from `/v1/tests/changes` (`whole: true`); otherwise the changes may bring it (new tests), else the job has nothing to run (a notice, `run=false`; without an api-key it fails naming the path). Nothing the job writes is committed. After a `patched` heal, `apply` asks `/v1/tests/changes` again and the tests re-run (`QUALIO_RUN_ROUND=2`). Without an api-key the folder is `working-directory` (or `e2e`) and nothing is reported.
- **Email in tests** ([spec](../specs/email-in-tests.md)): `/v1/tests/prepare` may answer `env`; `exportTestEnv` writes only `QUALIO_MAIL`, `QUALIO_MAIL_URL`, `QUALIO_MAIL_DOMAIN`, `QUALIO_MAIL_SERVER` (no newlines; a variable the job already sets wins) to `GITHUB_ENV` and `process.env`, so the run and re-run steps' tests (`support/email.ts`) read them. A hosted inbox's `QUALIO_MAIL_API_KEY` comes from the job's own env, never from Qualio. `test/prepare.test.mjs` (stub mode `email`) covers it.
- **Action → reporter:** the reporter ships in `runtime/qualio-reporter.ts`, a copy of `../qualio-webapp/packages/reporter/src/qualio-reporter.ts` (`pnpm reporter:sync` there; its tests check they match). `prepare` copies it to `<tests>/.qualio/qualio-reporter.ts` and outputs its path; the run steps set `QUALIO_REPORTER` (the generated `playwright.config.ts` adds it as a reporter) and `QUALIO_RUN_MANIFEST` (`$RUNNER_TEMP/qualio-manifest.json`: `{ bundleId, revisionIds }`, the changes the job applied, which the reporter sends with the run). It reports only when `QUALIO_API_URL` and `QUALIO_API_KEY` are set, and reads `QUALIO_COMMIT_SHA` (falling back to `GITHUB_SHA`) and the branch from `GITHUB_HEAD_REF`/`GITHUB_REF_NAME`. The generated `playwright.config.ts` reads `QUALIO_BASE_URL`. A team's own config that doesn't mention `QUALIO_REPORTER` gets the reporter on the command line: `prepare`'s `reporter-args` output (`--reporter=list,html,<reporter>`), used by the run and re-run steps.
- **Map (no first-suite setup, phase 54; [spec](../specs/adopting-existing-tests.md)):** every run with an api-key calls `scripts/qualio.mjs map` (step *Map the application*, `continue-on-error`) → `POST /v1/map/start`. When Qualio answers `map` (the project's first job, or the next target-branch job after **Map again**), the job runs the mapper Qualio returns (`npx playwright test -c qualio-map.config.ts`; it posts to `/v1/map/:crawlId/pages` and `/mapped` itself), then polls `/v1/map/:crawlId/status` until `done` or `failed`. It never fails the job (warnings) and generates no tests; output `map-state` (`mapped`, `skipped`, `failed`; a 404 from an older Qualio is `skipped`). `setup` is an alias of `map`, and the `setup-state` output is kept, always empty. Qualio reads the team's tests from the snapshot `prepare` sends (the Adopter); a missing tests folder with nothing from Qualio is a notice (`run=false`), not a failure.
- **Config (`config` / `config-file`):** the `config` command (step *Sync the Qualio config*, before the map step, only in jobs with a checkout) posts the YAML to `/v1/config/sync` (`branch`, `prNumber`, `headSha`, `source`, `raw`); Qualio parses and validates it (`@qualio/shared/workflow-config` in qualio-webapp, the only schema). When it answers `state: overview` with `paths` and `known` hashes, the job reads those `.md`/`.txt` files from the checkout and posts again with `overview: [{ path, sha256, content? }]` (content only for unknown hashes). 422 lists `problems` and fails the job; `warnings` become `::warning`. The step never runs in the comment job or on a closed pull request; `node --test test/config.test.mjs` covers it against the stub.
- **Dispatch:** Qualio's **Run tests** and post-heal re-runs dispatch the workflow file `qualio.yml` (`workflow_dispatch`).
- **Pull request sync and the GitHub outbox:** on `pull_request` events `scripts/qualio.mjs sync` posts the event's pull request (never repository contents, but its `merge_commit_sha` once merged) to `/v1/pr/sync`; `outbox` (start and end of every job, input `github-token`) reads `/v1/pr/outbox` (with `report: true, changes: true`), sends each item (`REPORT`, `COMMENT`, `STATUS`, `DISPATCH`, `LABEL`, `REACTION`, `TEST_CHANGES`) with the GitHub REST API and acks it at `/v1/pr/outbox/:id/ack`. `REPORT` is the pull request's one Qualio report comment, built by Qualio when the job reads the outbox: the job edits the comment whose id Qualio sends, else the bot comment starting with `<!-- qualio:report -->`, else posts it, and acks with its `commentId`; `REACTION` reacts to a person's `/qualio` command; `TEST_CHANGES` is a branch's changes to the tests (`{ branch, prNumber, testsDir, mode, qualioBranch, qualioPr, close, title, body, changes: [{ id, kind, title, message, body, suggest, via, files: [{ path, content, baseSha256 }] }] }`): fixes whose every hunk is on lines the pull request's diff shows (and whose files the head still has as `baseSha256`) become one review of ```` ```suggestion ```` comments (`scripts/diff.mjs`: `diffHunks`, `commentableLines`, `suggestionComments`); the rest are rebuilt as one commit each on `qualioBranch` (`qualio/pr-<n>`, or `qualio/<branch>` for the target branch) from the base branch's head with the Git data API, force-pushed, and opened or updated as a pull request into the branch; a change whose files changed otherwise is a `conflict`; `close` (or nothing left) closes it and deletes the branch; a Qualio pull request a person merged or closed is reported back first. The ack carries `changes: { delivered: [{ id, via: suggestion|qualio_pr|report, reviewId?, commitSha? }], conflicts, qualioPr, retired }`. `report-only` delivers via `report`. A 403/404 pushing the branch, or a refused pull request (GitHub's *Allow GitHub Actions to create and approve pull requests* is off, in the repository or its organization; the warning gives the compare link and Qualio's guide, `/docs/getting-started#allow-pull-requests`), also report them, and the ack adds `blocked: { reason: pull_request|push, status, message, qualioBranch, compareUrl }`: Qualio keeps those changes to offer, shows the project how to allow it, and the next job tries again. Older actions (no `report`) get each report as a new `COMMENT` and no reactions (403/429/5xx stay pending for the next job; other 4xx are acked with the error); On a pull request's job (not the comment job, not a closed one) since v1.7.1 the end outbox sends `prNumber` and waits up to 2 minutes while Qualio answers `waiting` (it is still reading that pull request's own ticket), so a pull request with nothing to test ends with a green `qualio/tests` status; it reads once when nothing is pending (`test/outbox.test.mjs`, stub mode `triage`). `errored` posts `/v1/runs/errored` when the job failed before results were reported. All three steps are `continue-on-error`. The served workflow grants `pull-requests`, `issues`, `statuses` and `actions` write for them.
- **Comment job:** `command: comment` (the served workflow's `comment` job, on `issue_comment`, no checkout) skips everything but `comment` (posts the event's comment to `/v1/pr/comment`) and the outbox, which then waits up to `reply-wait-minutes` while `/v1/pr/outbox` answers `waiting: true` (an agent is answering).
- **Live diagnosis:** while `wait` polls `/v1/tests/heal/status` it sends `browser: true` (input `live-diagnosis`, default `true`; the step gets `QUALIO_BASE_URL`, `QUALIO_TESTS_DIR`, `QUALIO_LIVE_DIAGNOSIS`). When the answer has `browser: { sessionId, roles: [{ role, usernameEnv, passwordEnv }] }`, `scripts/browser-host.mjs` (`startBrowserHost`) long-polls `/v1/browser/next` and answers each call at `/v1/browser/result` (`result` or `error`) until `done`, a 404, or the heal ends. The calls are `open` (`{ path, role }`: the page's snapshot) and `check` (`{ path, role, locators }`: loads the page, then resolves each locator with `browser_snapshot`'s `target`, which Playwright MCP parses as locator text and never evaluates; `checkableLocator` lets only `getBy…` chains through as a second fence; `locatorCount` turns the answer into `{ locator, count, element, suggestions, error }`; the result is JSON `{ checks }`, at most `MAX_LOCATORS`). `appPath` and the origin check refuse anything off `base-url`'s origin, and a redirect away from it returns an error, not the page. It runs one Playwright MCP server per role (`MCP_PACKAGE`, pinned; MCP's JSON-RPC over stdio is spoken directly, with no dependencies), started lazily with `--headless --isolated --executable-path <the tests folder's Playwright Chromium>` and, for a role, `--init-page` (a sign-in script reading `QUALIO_SIGNIN_*` from its env, set from the role's secrets). The server's env is `SAFE_ENV` only. It calls only `browser_navigate` and `browser_snapshot` (with or without `target`). Tests: `test/live.test.mjs` with `test/fake-mcp.mjs` (`QUALIO_MCP_COMMAND`, `QUALIO_BROWSER_EXECUTABLE` override the command and the browser).
- **Test chat looks:** the `look` command (step *Let Qualio's test chat look at the app*, at the end of every job that ran tests, `continue-on-error`, input `look-minutes`, default `10`, `0` off; also off with `live-diagnosis: false`) posts `/v1/browser/look` (`{ branch }`). An answer with `browser: { sessionId, roles }` (a test chat asked to see the running app on this branch; Qualio started the workflow for it) runs `startBrowserHost` until `/v1/browser/next` says `done` (the chat stopped looking) or `look-minutes` pass; `{}` or a 404 (an older Qualio) ends the step at once. Same calls (`open`, `check`) and fences as live diagnosis. `test/live.test.mjs` covers it against the stub.
- **Exploring the map (every map):** `map` sends `browser: true` with its status polls (when `live-diagnosis` is on: the step gets `QUALIO_LIVE_DIAGNOSIS`; the browser uses the mapper folder's Chromium) and, while the answer has `browser` (the map's `explore` state), runs `startBrowserHost`; it stops the host once the map is `done`. The host's `explore` call (`{ path, role, control }`) uses a separate browser per role (`serverFor(role, 'explore')`) whose init page (`EXPLORE_INIT`) signs in and then installs `WRITE_GUARD` (blocks non-GET fetch/XHR except GraphQL queries, beacons and POST form submits, logging `[qualio] blocked …`); it resolves the control (exactly one element), refuses what `clickRefusal` says (not a button, link, tab or menu; sign-out; links off the origin), clicks (`browser_click`), waits a second, and answers `{ url, title, element, snapshot, blocked }` (blocked writes from `browser_console_messages`). `test/live.test.mjs` compiles the scripts the browser loads (`SIGN_IN`, `EXPLORE_INIT`, `WRITE_GUARD`), runs the guard in a fake window and explores through the fake MCP server.
- **Healing:** after a failing run, `wait` polls `/v1/tests/heal/status`; the action sets `QUALIO_RUN_FILE` (the reporter writes `{ runId, status, url, heal }` there). `/v1/tests/bundle` and `/v1/tests/promote` are gone (410): tests aren't served, and nothing is promoted when a pull request closes (`/v1/pr/sync` reports it). Jobs of Qualio's own pull requests (`qualio/*` heads) only sync.
- **Auto-sharding** ([spec](../specs/auto-sharding.md)): the served workflow's `plan` job runs the action with `command: plan`: check, pr sync, config sync, the start outbox, `prepare` and the dependencies, then `qualio.mjs plan` lists the tests (`listTests`: `npx playwright test --list --reporter=json`, files relative to the tests folder with their test counts; `QUALIO_PLAYWRIGHT_LIST` reads a saved list in tests) and posts `/v1/tests/plan` (`branch`, `commitSha`, `ghRunId`, `ghRunAttempt`, `files`), outputting `run`, `shards` (the matrix, JSON) and `plan-id` (empty for one job). No map, browsers, run, summary or look in the plan job; a failed listing, a 404 (older Qualio) or an error means one job. The `e2e` jobs pass `shard` and `shard-plan`: they skip pr sync, config sync and the start outbox; only shard 1 maps and looks; `qualio.mjs shard` posts `/v1/tests/plan/shard` and writes each file as an anchored absolute-path regex to `$RUNNER_TEMP/qualio-shard-args.txt` (Playwright's CLI filters are regexes on the absolute path), which the run and re-run steps pass (`mapfile`); a shard that can't read its files fails. The run steps set `QUALIO_SHARD_INDEX`, `QUALIO_SHARD_TOTAL`, `QUALIO_SHARD_PLAN` and `QUALIO_JOB_STARTED_AT` (from the runner's `Runner.Worker` process, the check step's `started-at`) for the reporter; `errored` sends `shard` (without `total` when the plan was never read); the end outbox sends `lease: true` (`QUALIO_SHARDED`). The report artifact is `playwright-report-shard-<n>`. `test/shards.test.mjs` covers it against the stub (mode `shards`), and the Test workflow's `shards-plan`/`shards` jobs split `test/shard-fixture` over two jobs.
- When you add or rename an input, update `workflowFile()` and its tests in qualio-webapp, the docs' action reference (`apps/web/src/lib/docs/action-reference.ts`) and this README.

## Rules

- **Backwards compatible within `v1`:** customers' `qualio.yml` is never overwritten by Qualio, so old workflows must keep working. Only add optional inputs; breaking changes need `v2`.
- **No secrets in logs:** never `echo` inputs; pass `api-key` to steps only through `env`.
- **Composite only:** steps use `shell: bash` and `working-directory: ${{ steps.tests.outputs.dir }}` (the tests folder `prepare` found); third-party actions are pinned to a major version (`actions/*@v4`).
- **Never push anywhere but `qualio/*`:** the action pushes only the Qualio pull request's branch it builds (`qualioBranch`), never a developer's branch or the target branch.
- **Never fail silently:** a failing test must fail the job; the HTML report upload runs `if: !cancelled()`.
- **Playwright version:** browsers are cached per the tests folder's `@playwright/test` version. Playwright MCP (`MCP_PACKAGE`) brings its own Playwright but drives that same Chromium (`--executable-path`, checked with 0.0.84 on 1.64.1's Chromium); when you bump either, check them together. Keep `test/fixture` on the same version as qualio-webapp (`packages/reporter`, `packages/crawler`).
- **Steps:** a preflight checks the tests folder (and warns, without echoing it, when the key is empty); the test output is `tee`'d to `$RUNNER_TEMP/qualio-playwright.log` so the job summary and the `qualio-run-url` output can pick up the reporter's `[qualio] Results reported: <url>` line. Keep that log line format in step with `../qualio-webapp/packages/reporter`.
- **Job summary style:** summaries use the same table cells as Qualio's comments (local `cell` in `scripts/qualio.mjs`, a copy of `@qualio/shared/github-markdown`'s).
- **Never fail silently with healing either:** the first run's step continues on error so the heal and re-run can follow, and the final `Result` step fails the job unless the re-run passed. A `proposed` heal (the project asks first) ends the wait at once and fails the job with a pointer to Qualio; there is no re-run until someone decides.
- Check changes with `node --test test/*.test.mjs` (diffs, prepare, outbox with suggestions and the Qualio pull request, config, against `test/stub-qualio.mjs`, which also stands in for GitHub) and the `Test` workflow (actionlint, `uses: ./` on `test/fixture`, the missing-folder failure path, the heal on `test/heal-fixture`, the map and the empty folder against the stub).

## Releasing

Lives at `Qualio-AI/qualio-action`, referenced as `qualio-ai/qualio-action@v1` (owner names are case-insensitive); customers outside the organization need the repository public. Publishing a GitHub release `vX.Y.Z` runs `.github/workflows/release.yml`, which moves the major tag (`v1`); `v1` is on `v1.7.0` (phases 63–71: binary test files, email in tests, `test-passwords`); `v1.7.1` (phase 72: the end outbox waits for Qualio to read a pull request) is next. The README's Part 3 has the step-by-step publishing guide.
- **Test accounts** (phase 71): passwords come from the input `test-passwords` (the `QUALIO_TEST_PASSWORDS` secret, one `Role=password` line each). The step *Read the test account passwords* (`qualio.mjs passwords`, `scripts/accounts.mjs`: `parsePasswords`, `roleEnvKey` in step with `@qualio/shared`) masks each password and appends `E2E_<KEY>_PASSWORD` to `GITHUB_ENV` unless the job env already sets it; an unreadable line is a warning with its line number only. Usernames come from the Qualio config (`roles[].username`): `/v1/tests/prepare` answers them in `env` (`E2E_<KEY>_USERNAME`, allowed by `TEST_ENV`, with a warning when a username has no password), and the mapper and the browser host get them in their roles (`username`), the job's own variable winning. `test/passwords.test.mjs` covers it.
