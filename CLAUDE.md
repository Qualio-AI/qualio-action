# CLAUDE.md — qualio-action

The GitHub Action (composite, `action.yml`) that customers' `.github/workflows/qualio.yml` calls to run Qualio's generated Playwright tests on their own runners and report to Qualio. Product rules live in the global `../CLAUDE.md`; the platform is `../qualio-webapp`.

## Contract with qualio-webapp

- **Workflow → action:** Qualio writes the workflow in `../qualio-webapp/packages/agents/src/coder/scaffold.ts` (`servedWorkflowFile()`, `QUALIO_ACTION_REF`). It passes `api-key`, `api-url`, `base-url` and the `config` block (with `tests.path`), grants `contents: write` (only for Qualio's `qualio/*` branches) and puts the test account secrets (`E2E_<ROLE>_USERNAME/_PASSWORD`) in the job-level `env`, which this action's steps inherit. `tests-source` is ignored (a notice asks to remove it) and `working-directory` is the folder only when the config doesn't set `tests.path`.
- **Tests live in the repository** ([spec](../specs/tests-in-the-repository.md)): `prepare` (step *Prepare the tests*) asks `/v1/tests/prepare` for the folder (`testsDir`, `managed`: qualio.yml's `tests.path` wins over `working-directory`; `moving`: the project's tests are still in Qualio), sends `/v1/tests/snapshot` (`files: [{ path, sha256 }]`, then again with `content` for the hashes Qualio answers `missing`; never `node_modules`, Playwright's output or `.qualio`), and writes the answer's `files` (Qualio's open changes on the branch; `content: null` deletes) on top of the checkout. Without the folder: a `moving` project gets the whole folder from `/v1/tests/changes` (`whole: true`); otherwise the changes may bring it (the first suite, new tests), else the job fails naming the path. Nothing the job writes is committed. After a `patched` heal, `apply` asks `/v1/tests/changes` again and the tests re-run (`QUALIO_RUN_ROUND=2`). Without an api-key the folder is `working-directory` (or `e2e`) and nothing is reported.
- **Action → reporter:** the reporter ships in `runtime/qualio-reporter.ts`, a copy of `../qualio-webapp/packages/reporter/src/qualio-reporter.ts` (`pnpm reporter:sync` there; its tests check they match). `prepare` copies it to `<tests>/.qualio/qualio-reporter.ts` and outputs its path; the run steps set `QUALIO_REPORTER` (the generated `playwright.config.ts` adds it as a reporter) and `QUALIO_RUN_MANIFEST` (`$RUNNER_TEMP/qualio-manifest.json`: `{ bundleId, revisionIds }`, the changes the job applied, which the reporter sends with the run). It reports only when `QUALIO_API_URL` and `QUALIO_API_KEY` are set, and reads `QUALIO_COMMIT_SHA` (falling back to `GITHUB_SHA`) and the branch from `GITHUB_HEAD_REF`/`GITHUB_REF_NAME`. The generated `playwright.config.ts` reads `QUALIO_BASE_URL`.
- **First test suite (setup):** every run with an api-key first calls `scripts/qualio.mjs setup` → `POST /v1/setup/start`. Until the project has a ready suite, the job runs the mapper Qualio returns (`npx playwright test -c qualio-map.config.ts`; it posts to `/v1/setup/:suiteId/pages` and `/mapped` itself), polls `/v1/setup/:suiteId/status`, and for each `validate` asks `/v1/tests/changes` with `suiteId` (and `has`, the paths the folder already has) and writes the suite (with the scaffold of a new folder) into the tests folder of the checkout, then runs it with `QUALIO_RUN_ROUND=<check>`. Once ready, Qualio offers the suite as a Qualio pull request into the setup branch. The setup pull request is opened by a person (Qualio's onboarding gives a pre-filled GitHub link; Qualio never writes to the developer's branches).
- **Config (`config` / `config-file`):** the `config` command (step *Sync the Qualio config*, before the setup, only in jobs with a checkout) posts the YAML to `/v1/config/sync` (`branch`, `prNumber`, `headSha`, `source`, `raw`); Qualio parses and validates it (`@qualio/shared/workflow-config` in qualio-webapp, the only schema). When it answers `state: overview` with `paths` and `known` hashes, the job reads those `.md`/`.txt` files from the checkout and posts again with `overview: [{ path, sha256, content? }]` (content only for unknown hashes). 422 lists `problems` and fails the job; `warnings` become `::warning`. The step never runs in the comment job or on a closed pull request; `node --test test/config.test.mjs` covers it against the stub.
- **Dispatch:** Qualio's **Run tests** and post-heal re-runs dispatch the workflow file `qualio.yml` (`workflow_dispatch`).
- **Pull request sync and the GitHub outbox:** on `pull_request` events `scripts/qualio.mjs sync` posts the event's pull request (never repository contents, but its `merge_commit_sha` once merged) to `/v1/pr/sync`; `outbox` (start and end of every job, input `github-token`) reads `/v1/pr/outbox` (with `report: true, changes: true`), sends each item (`REPORT`, `COMMENT`, `STATUS`, `DISPATCH`, `LABEL`, `REACTION`, `TEST_CHANGES`) with the GitHub REST API and acks it at `/v1/pr/outbox/:id/ack`. `REPORT` is the pull request's one Qualio report comment, built by Qualio when the job reads the outbox: the job edits the comment whose id Qualio sends, else the bot comment starting with `<!-- qualio:report -->`, else posts it, and acks with its `commentId`; `REACTION` reacts to a person's `/qualio` command; `TEST_CHANGES` is a branch's changes to the tests (`{ branch, prNumber, testsDir, mode, qualioBranch, qualioPr, close, title, body, changes: [{ id, kind, title, message, body, suggest, via, files: [{ path, content, baseSha256 }] }] }`): fixes whose every hunk is on lines the pull request's diff shows (and whose files the head still has as `baseSha256`) become one review of ```` ```suggestion ```` comments (`scripts/diff.mjs`: `diffHunks`, `commentableLines`, `suggestionComments`); the rest are rebuilt as one commit each on `qualioBranch` (`qualio/pr-<n>`, or `qualio/<branch>` for the target branch) from the base branch's head with the Git data API, force-pushed, and opened or updated as a pull request into the branch; a change whose files changed otherwise is a `conflict`; `close` (or nothing left) closes it and deletes the branch; a Qualio pull request a person merged or closed is reported back first. The ack carries `changes: { delivered: [{ id, via: suggestion|qualio_pr|report, reviewId?, commitSha? }], conflicts, qualioPr, retired }`. `report-only`, a 403/404 pushing the branch, or a refused pull request (GitHub's *Allow GitHub Actions to create and approve pull requests* is off; the warning gives the compare link) deliver via `report`. Older actions (no `report`) get each report as a new `COMMENT` and no reactions (403/429/5xx stay pending for the next job; other 4xx are acked with the error); `errored` posts `/v1/runs/errored` when the job failed before results were reported. All three steps are `continue-on-error`. The served workflow grants `pull-requests`, `issues`, `statuses` and `actions` write for them.
- **Comment job:** `command: comment` (the served workflow's `comment` job, on `issue_comment`, no checkout) skips everything but `comment` (posts the event's comment to `/v1/pr/comment`) and the outbox, which then waits up to `reply-wait-minutes` while `/v1/pr/outbox` answers `waiting: true` (an agent is answering).
- **Live diagnosis:** while `wait` polls `/v1/tests/heal/status` it sends `browser: true` (input `live-diagnosis`, default `true`; the step gets `QUALIO_BASE_URL`, `QUALIO_TESTS_DIR`, `QUALIO_LIVE_DIAGNOSIS`). When the answer has `browser: { sessionId, roles: [{ role, usernameEnv, passwordEnv }] }`, `scripts/browser-host.mjs` (`startBrowserHost`) long-polls `/v1/browser/next` and answers each call at `/v1/browser/result` (`result` or `error`) until `done`, a 404, or the heal ends. The calls are `open` (`{ path, role }`: the page's snapshot) and `check` (`{ path, role, locators }`: loads the page, then resolves each locator with `browser_snapshot`'s `target`, which Playwright MCP parses as locator text and never evaluates; `checkableLocator` lets only `getBy…` chains through as a second fence; `locatorCount` turns the answer into `{ locator, count, element, suggestions, error }`; the result is JSON `{ checks }`, at most `MAX_LOCATORS`). `appPath` and the origin check refuse anything off `base-url`'s origin, and a redirect away from it returns an error, not the page. It runs one Playwright MCP server per role (`MCP_PACKAGE`, pinned; MCP's JSON-RPC over stdio is spoken directly, with no dependencies), started lazily with `--headless --isolated --executable-path <the tests folder's Playwright Chromium>` and, for a role, `--init-page` (a sign-in script reading `QUALIO_SIGNIN_*` from its env, set from the role's secrets). The server's env is `SAFE_ENV` only. It calls only `browser_navigate` and `browser_snapshot` (with or without `target`). Tests: `test/live.test.mjs` with `test/fake-mcp.mjs` (`QUALIO_MCP_COMMAND`, `QUALIO_BROWSER_EXECUTABLE` override the command and the browser).
- **Healing:** after a failing run, `wait` polls `/v1/tests/heal/status`; the action sets `QUALIO_RUN_FILE` (the reporter writes `{ runId, status, url, heal }` there). `/v1/tests/bundle` and `/v1/tests/promote` are gone (410): tests aren't served, and nothing is promoted when a pull request closes (`/v1/pr/sync` reports it). Jobs of Qualio's own pull requests (`qualio/*` heads) only sync.
- When you add or rename an input, update `workflowFile()` and its tests in qualio-webapp, the Getting Started page (`apps/web/src/app/docs/getting-started/page.tsx`) and this README.

## Rules

- **Backwards compatible within `v1`:** customers' `qualio.yml` is never overwritten by Qualio, so old workflows must keep working. Only add optional inputs; breaking changes need `v2`.
- **No secrets in logs:** never `echo` inputs; pass `api-key` to steps only through `env`.
- **Composite only:** steps use `shell: bash` and `working-directory: ${{ steps.tests.outputs.dir }}` (the tests folder `prepare` found); third-party actions are pinned to a major version (`actions/*@v4`).
- **Never push anywhere but `qualio/*`:** the action pushes only the Qualio pull request's branch it builds (`qualioBranch`), never a developer's branch or the target branch.
- **Never fail silently:** a failing test must fail the job; the HTML report upload runs `if: !cancelled()`.
- **Playwright version:** browsers are cached per the tests folder's `@playwright/test` version. Playwright MCP (`MCP_PACKAGE`) brings its own Playwright but drives that same Chromium (`--executable-path`, checked with 0.0.84 on 1.64.1's Chromium); when you bump either, check them together. Keep `test/fixture` on the same version as qualio-webapp (`packages/reporter`, `packages/crawler`).
- **Steps:** a preflight checks the tests folder (and warns, without echoing it, when the key is empty); the test output is `tee`'d to `$RUNNER_TEMP/qualio-playwright.log` so the job summary and the `qualio-run-url` output can pick up the reporter's `[qualio] Results reported: <url>` line. Keep that log line format in step with `../qualio-webapp/packages/reporter`.
- **Job summary style:** the setup's summary uses the same icons and GitHub alerts as Qualio's comments (local `alert`, `cell`, `details` in `scripts/qualio.mjs`, copies of `@qualio/shared/github-markdown`); the webapp's onboarding E2E checks it.
- **Never fail silently with healing either:** the first run's step continues on error so the heal and re-run can follow, and the final `Result` step fails the job unless the re-run passed. A `proposed` heal (the project asks first) ends the wait at once and fails the job with a pointer to Qualio; there is no re-run until someone decides.
- Check changes with `node --test test/*.test.mjs` (diffs, prepare, outbox with suggestions and the Qualio pull request, config, against `test/stub-qualio.mjs`, which also stands in for GitHub) and the `Test` workflow (actionlint, `uses: ./` on `test/fixture`, the missing-folder failure path, the heal on `test/heal-fixture` and the setup against the stub).

## Releasing

Lives at `Qualio-AI/qualio-action`, referenced as `qualio-ai/qualio-action@v1` (owner names are case-insensitive); customers outside the organization need the repository public. Publishing a GitHub release `vX.Y.Z` runs `.github/workflows/release.yml`, which moves the major tag (`v1`); `v1` is on `v1.1.0`. The README's Part 3 has the step-by-step publishing guide.
